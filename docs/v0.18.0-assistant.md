# AegisOps v0.18.0 — secure operations assistant

Open **http://127.0.0.1:8001/dashboard**, sign in with the existing separate
dashboard password, and choose **Assistant**. Alternatively, open an incident
and choose **Ask assistant about this incident**. No API token is entered in
the browser. The private `.env.dashboard-login` file remains ignored; never
copy its contents into source, screenshots, logs or chat.

## What the assistant does

The assistant answers operations questions using live PostgreSQL records and
the existing local runbook retrieval path. It can list the latest critical
incidents, find incidents with failed/running jobs, retrieve a specific
incident and its saved evidence, show its automatic job, search runbooks,
and distinguish observed metrics from saved hypotheses and suggested checks.

Examples:

- Show me the latest critical incidents.
- What happened to incident 54?
- What evidence supports its investigation?
- Are any AI investigation jobs failing?
- What does our runbook recommend checking?
- What is the difference between observed symptoms and suspected cause?

Use an explicit incident ID or the optional context field for scoped
questions. Follow-ups retain the last incident. A global list question
clears that incident context. Clear conversation resets both context and
history. Ambiguous requests for incident evidence ask for context rather
than silently choosing a record. Unknown or out-of-range IDs are reported
without creating or linking a nonexistent record.

Conversation history is kept in the authenticated dashboard session, capped
at six turns. Reloading the page preserves it until logout, session expiry,
clear, or API restart. It is never written to PostgreSQL or browser storage.
Enter sends a question; Shift+Enter inserts a line break. Responses have
source buttons that open the relevant incident and saved investigation.
Runbook references identify actual source filenames and quote their passages;
there is no arbitrary file-download endpoint.

## Architecture and grounding contract

This is deliberately an **extractive, constrained assistant**, not a general
autonomous agent. `assistant_service.py` recognizes bounded English
operations intents and chooses tools on the server. Qwen does not choose
tool names or execute anything. The sequence is:

1. Validate the session, Origin/Host, CSRF header and typed request body.
2. Run at most four allowlisted read tools, validating every argument and
   rechecking session authorization before each call.
3. Build a bounded registry of facts with database IDs or actual runbook
   filenames. Release database transactions before inference/embeddings.
4. Ask the configured local Qwen/Ollama model to select relevant **fact IDs**
   using a strict JSON schema. User questions, previous questions, stored
   hypotheses and runbook passages are explicitly untrusted data.
5. Reject any unknown ID, unexpected output field or malformed model result.
   The server assembles the answer only from its retrieved fact registry.
   Required metrics, missing-evidence notices and the latest saved evidence
   and hypothesis cannot be silently removed by model selection.
6. Recheck that the session remains active before returning/storing the turn.

The model cannot introduce free-form factual claims or links. This is stronger
than merely asking a model to cite its answer, but intentionally less flexible
than unrestricted prose generation. It provides real conversational retrieval,
follow-up context and model-selected evidence without speculative summaries.
Evidence is quoted from saved records, not independently revalidated by this
assistant. Root-cause hypotheses remain unconfirmed. Suggested checks and
runbook text require human review and are never executed.

If model selection fails or Ollama is unavailable, the response is marked
`degraded` and shows the retrieved facts with a fixed fallback notice.
If runbook embeddings fail, a specific unavailability fact is shown without
inventing runbook advice. A database outage produces a fixed HTTP 503 rather
than a model answer. Raw exceptions, URLs, provider output and credential
details are never included in error responses.

## Tool definitions and bounds

All tools require a currently active dashboard session even when called
internally. There is no public arbitrary-tool execution endpoint. Unknown
tool names and extra fields fail validation. SQL uses fixed SQLAlchemy
SELECT statements; user strings never become SQL, paths, URLs or commands.

| Tool | Typed arguments | Bounded result |
| --- | --- | --- |
| `list_incidents` | Optional severity, incident status, job status; integer limit 1–5 | Matching count and at most five newest incidents with job status |
| `get_incident` | Positive 32-bit incident ID | One incident or explicit not-found |
| `get_investigations` | Incident ID; limit 1–2 | Latest two saved investigations; six evidence entries each; bounded text |
| `get_investigation_job` | Incident ID | One automatic job, attempts and sanitized failure category; no claim token |
| `search_runbooks` | Query 1–240 characters; limit 1–2 | Two actual source filenames/passages, through existing RAG; at most 24 chunks embedded |

Most fact text is capped at 1,600 characters; stored hypothesis/recommendation
fields are first capped at 1,200. Responses contain at most twelve facts.
Truncated excerpts are marked. Non-list malformed stored evidence becomes
unavailable evidence rather than executable data or a crash. Configured
environment credentials are redacted before text enters conversation/model
context; this is a known-value safeguard, not a general secret/PII detector.

There is one concurrent ask per session and two assistant requests globally
per API process. Busy requests receive 409/429. The orchestration uses a
60-second budget, checked between tools and model chunks. RAG gets a
15-second sub-budget, and the model has bounded connect/read timeouts, a
32 KiB response cap, 256 generated tokens and a 6,144-token context setting.
Socket read timeouts are not a hard cancellation deadline for every upstream
operation. The browser waits at most 75 seconds and retains its input after
failure. No request starts another tool after the budget expires.

## Authentication, HTTP and local deployment

The existing one-hour HttpOnly, SameSite=Strict cookie is reused. The shared
`require_csrf` dependency protects both assistant POST routes and logout.
Cookie sessions still cannot authorize existing Bearer API routes. No
operator/n8n token, database credential or Ollama configuration is sent to
the frontend. The dashboard's strict CSP, no-store policy and safe DOM text
rendering remain in place; assistant categories are allowlisted and citation
links are constructed from server-issued integer IDs, never model URLs.

| Endpoint | Purpose |
| --- | --- |
| `GET /dashboard/api/assistant` | Read the current session's last six turns and context |
| `POST /dashboard/api/assistant` | Ask `{message, incident_id?}`; session + same-origin + CSRF required |
| `POST /dashboard/api/assistant/clear` | Clear this session's conversation; same protections |

Requests accept at most 2,000 message characters and 12 KiB of body data.
Validation errors do not echo the message. Replies contain user text after
known-secret redaction and a typed answer with status, facts, sources, tool
names and context. Conversation expiry or logout during inference prevents
the completed answer from being stored or returned to that expired session.

Reuse existing model settings: `OLLAMA_BASE_URL`, `OLLAMA_CHAT_MODEL`,
`OLLAMA_EMBED_MODEL`. Native Windows defaults use localhost; Compose keeps
`DOCKER_OLLAMA_BASE_URL=http://host.docker.internal:11434`. The assistant
accepts only configured local model hostnames (`localhost`, loopback,
`host.docker.internal`, or `ollama`) and never follows model HTTP redirects.
The existing worker's default RAG behavior is unchanged; optional deadline
and chunk-limit parameters are used only by assistant calls.

The local API and assets are already deployed. To update from source while
the existing database and worker remain running:

```powershell
docker compose build api
docker compose up -d --no-deps api
```

Only the API needs updating. Do not restart n8n, recreate databases, replace
volumes, or run migrations. Native Windows alternative (only if port 8001
is free):

```powershell
.\.venv\Scripts\python.exe -B -m uvicorn app:app --host 127.0.0.1 --port 8001
```

## Deliberate limitations

- This is a bounded English operations-intent recognizer and extractive
  evidence selector, not an unrestricted chatbot, autonomous planner or
  tool-calling framework. Unrecognized wording may need an explicit incident
  ID or one of the supported question forms.
- Source identity and excerpt fidelity are checked, not the correctness of
  a historical hypothesis or runbook. Retrieved passages may be irrelevant,
  stale or malicious; their text remains untrusted. There is no causal proof.
- Read-only global listing shows at most five records and saved history at
  most two investigations per retrieval. There is no n8n execution history.
- Sessions/history and concurrency gates are process-local. The existing
  single-process, shared-password, trusted-workstation, local-HTTP boundary
  remains; restarting the API revokes sessions. No public deployment or
  multi-user identity system is introduced.
- This milestone does not stream tokens or provide hard upstream inference
  cancellation. Logout discards the eventual reply but may not stop a model
  request already in progress. A retried read-only chat question may repeat
  inference, but never creates a job or runs remediation.
- Chromium desktop/mobile was tested, not Safari/Firefox or physical-device
  accessibility certification. No credentials were embedded in screenshots.
