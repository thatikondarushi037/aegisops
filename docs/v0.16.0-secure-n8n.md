## Authentication

All incident endpoints require `Authorization: Bearer <token>`.
`AEGISOPS_N8N_TOKEN` permits only `POST /incidents`.
`AEGISOPS_OPERATOR_TOKEN` permits ingestion, reads, updates, deletion, manual
investigation, investigation history, and job status. Both must be nonempty
and distinct, otherwise protected requests fail closed with 503. Missing or
invalid credentials receive 401 with a Bearer challenge; a valid ingestion
credential on an operator endpoint receives 403. Comparisons use
`secrets.compare_digest` over bytes, and errors never include supplied tokens.
The root liveness endpoint and API documentation remain public locally.

Credentials are supplied through the existing ignored `.env` for Windows
and `.env.docker` for Compose. Process environment takes precedence for the
native API. Restart after changing credentials. No frontend is added.
A future local dashboard or assistant backend must attach the operator
Bearer header to its API calls. Keep that token on the trusted backend,
outside browser bundles, URLs, chat transcripts, and browser persistent
storage. This milestone has one trusted operator role, not per-user accounts,
tenant isolation, OAuth, or production authorization.

## Import and configure the new workflow

The local v0.16 workflow is already installed and published as
`ae335dfb12353dd8` (**AegisOps v0.16 secure alert ingestion**). Open
`http://127.0.0.1:5678/workflow/ae335dfb12353dd8` after signing in.
Do not import it again into this instance. The portable export remains
`workflows/aegisops-v0.16.0.json`, without runtime IDs or secrets.
For a fresh instance only, import it as a new workflow using the editor,
then follow the steps below. Keep unrelated workflows intact.

1. Create an n8n **Header Auth** credential with header name `Authorization`
   and value `Bearer ` followed by the private `AEGISOPS_N8N_TOKEN` value.
   Store this in n8n's credential manager, not workflow JSON.
2. Select that credential in **Ingest incident**. Verify the URL against the
   network table. Do not use the operator credential.
3. Keep successful, failed, manual, and progress execution persistence
   disabled as specified by the export. Raw HTTP node errors may contain
   request details during interactive debugging; do not enable verbose
   logging or share raw node output. The sanitized webhook response retains
   the delivery category/status without storing raw errors or tokens.
4. Test using **Listen for test event** and `/webhook-test/aegisops-v016-alert`.
   Then publish/activate the new workflow using the installed n8n UI for
   the production `/webhook/aegisops-v016-alert` path.

Webhook validation rejects missing fields, blank services, numeric strings,
nonfinite/out-of-range error rates, and negative/noninteger latency with 422.
Only the three metric fields are forwarded. HTTP Request uses a ten-second
timeout, no redirects (to prevent forwarding credentials), and at most three
attempts separated by one second. n8n's native retry also retries permanent
HTTP failures within that same bound; correct credentials before repeating.
HTTP 201 and 200 both return `incident_id`, `api_status`, and `delivery`.
Exhausted failures return a sanitized 502; actual status may be unavailable
when n8n emits only an error item. Failure responses never echo API bodies,
request headers, raw exceptions, or submitted extra fields.

The simulator now actually uses its retry-enabled Session. It retries
connection failures and 429/502/503/504 responses up to three times after the
initial attempt, ignores unbounded Retry-After delays, and does not retry
ambiguous read timeouts. Combined with n8n, delivery attempts can multiply
to at most twelve API calls. API ingestion remains the sole job creator;
the workflow never calls manual investigation or Ollama.

Existing open-service deduplication returns the same incident and creates no
additional job. The existing job uniqueness constraint remains unchanged.
This is not event-ID idempotency across incident closure/deletion: a delayed
delivery after closure can create a new incident. Keep the incident open
during the bounded delivery window. Durable upstream event identities are
a future schema/API extension, not silently introduced here.

test path and click **Listen for test event** before each request.
With the worker stopped, the new job must be pending immediately, even if
Ollama is unavailable. Start the worker and poll history with an operator
credential loaded locally without printing it:

```powershell
$operatorToken = .\.venv\Scripts\python.exe -B -c "from dotenv import dotenv_values; print(dotenv_values('.env')['AEGISOPS_OPERATOR_TOKEN'])"
$headers = @{Authorization = "Bearer $operatorToken"}
# Replace with the incident_id returned by n8n:
$incidentId = 123
Invoke-RestMethod "http://127.0.0.1:8001/incidents/$incidentId/investigation-job" -Headers $headers
Invoke-RestMethod "http://127.0.0.1:8001/incidents/$incidentId/investigations" -Headers $headers
Remove-Variable operatorToken,headers
```

Expect completed job and one saved automatic investigation requiring human
approval. Repeat ingestion and confirm unchanged job/result ID and history
count. If failed, report the sanitized job category; do not claim inference
success. Use a fresh service name if an existing incident is already open.

Send malformed webhook JSON `{}` and expect 422 without API ingestion.
Use the new workflow's test copy with an unused local API port to verify
bounded connection retries and a sanitized 502, then restore its URL.
Never stop a shared database to simulate failure. For an ambiguous delivery,
repeat the same valid service payload and confirm the same incident/job.
Call protected API routes without a header and with a wrong token (401),
then use the n8n credential on incident reads or manual investigation (403).
