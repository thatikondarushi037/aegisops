# AegisOps v0.17.0 — operations dashboard

## Open the local dashboard

The deployed dashboard is at **http://127.0.0.1:8001/dashboard**. Use that
exact address: `localhost` is a different origin and is intentionally
rejected unless explicitly configured. All data views require login.

A separate dashboard password was generated during local verification.
Open the ignored `.env.dashboard-login` file locally to obtain it; do not
paste its contents into chat, logs, screenshots, source, or command arguments.
This is not either of the existing API Bearer tokens. The password field
clears after submission, browser storage is unused, and logout clears the
visible data and revokes the server-side session.

For a fresh setup from the repository root:

```powershell
# Choose a separate password interactively; input is hidden.
.\.venv\Scripts\python.exe -B configure_dashboard.py
# Alternative: generate one into private .env.dashboard-login without printing it.
# .\.venv\Scripts\python.exe -B configure_dashboard.py --generate

# Existing PostgreSQL must already be running. Update only the API.
docker compose build api
docker compose up -d --no-deps api
```

The existing Dockerfile already copies the frontend and Python modules;
there is no Node server, build step, CDN, external font, or new runtime
dependency. `.dockerignore` excludes all `.env.*` files and private QA
dependencies. No database migration is needed; the existing Alembic head
remains `d150b8e2a731`. Do not run `down -v`, rebuild the worker, or recreate
n8n to serve this dashboard.

For native Windows startup, use the existing `.env` database configuration:

```powershell
.\.venv\Scripts\python.exe -B -m uvicorn app:app --host 127.0.0.1 --port 8001
```

Do not run that command while the Docker API already owns port 8001.
The established worker continues separately; the frontend does not start it.

## Screens and behavior

- **Overview:** real total/open/critical/warning counts, four-state job
  distribution, and the six newest incidents. Critical and warning counts
  include all historical incidents, not just open ones. The successful
  refresh timestamp describes data retrieval, not a claim of service health.
- **Incident Explorer:** literal, case-insensitive service search; severity
  and status filters (including legacy `superseded` records); 20-row pages.
  Select a service to open its incident workspace, observed facts, automatic
  job, saved evidence, AI hypothesis, recommendations, confidence, approval
  requirement and five-item history pages. No-job/no-history states are
  supported without backfilling or modifying old records.
- **Automation Monitor:** pending/running/completed/failed totals and
  20-row job pages with attempt counts, timestamps and sanitized error
  categories. It explicitly does not show n8n execution history.

Visible views refresh eight seconds after the previous refresh finishes.
Polling requests do not overlap across intervals; hidden pages stop polling.
Filters and pagination survive refresh. Requests time out after seven
seconds. Failed refreshes keep prior data with a stale indicator; session
expiry returns to login. Navigation, tables, dialogs, focus rings, labels,
and status text work without color alone. Reduced-motion preferences are
honored. Wide tables scroll within their panel on mobile, not the whole page.

The dashboard is intentionally read-only. No manual investigation trigger,
incident mutation, automatic remediation, or conversational assistant is
part of v0.17.0.

## Authentication and browser security

`DASHBOARD_PASSWORD_HASH` is a salted scrypt hash in ignored `.env` and
`.env.docker`. The setup script preserves existing hash values, appends
missing entries, and does not print the password or hash. Docker env-file
values are single-quoted so `$` separators remain literal. Never reuse the
n8n or operator API token as a dashboard password.

`DASHBOARD_ORIGIN` defaults to `http://127.0.0.1:8001`. Login requires matching
Origin and Host, and failed login attempts are limited to five per client
address per five minutes. Successful login rotates the session identifier.
The server stores at most 100 sessions, with an absolute one-hour lifetime.
The opaque cookie is HttpOnly, SameSite=Strict and scoped to `/dashboard`.
Logout requires the same origin and a constant-time checked CSRF header;
other dashboard APIs are GET-only. Browser sessions cannot access the
existing Bearer API routes or cause ingestion/investigation operations.

Local HTTP uses a non-Secure cookie so it works at the documented loopback
address. `DASHBOARD_COOKIE_SECURE=1` is available only when HTTPS is actually
provided. This setting alone does not make external deployment supported.
Sessions and throttles are in one API process, not PostgreSQL. Restarting
the API logs everyone out. Multiple API workers are unsupported for this
MVP session store; the independent investigation worker is unaffected.

Dashboard responses use `Cache-Control: no-store`, a strict same-origin CSP
without inline scripts, `nosniff`, no-referrer, and frame-ancestor blocking.
User and model text is rendered with `textContent` and element creation,
never `innerHTML`. Errors shown in the browser are fixed messages rather
than raw backend details. The UI never receives either API token.

## New endpoints

| Endpoint | Access / purpose |
| --- | --- |
| `GET /dashboard` | Public login shell; contains no incident data |
| `GET /dashboard/assets/{file}` | Local HTML/CSS/JS asset directory only |
| `POST /dashboard/login` | Same-origin dashboard password login |
| `GET /dashboard/session` | Authenticated session state and CSRF token |
| `POST /dashboard/logout` | Session + same-origin + CSRF required |
| `GET /dashboard/api/overview` | Session; incident and job aggregates |
| `GET /dashboard/api/incidents` | Session; service/severity/status filters, limit 1–100 |
| `GET /dashboard/api/jobs` | Session; job status filter, limit 1–100 |
| `GET /dashboard/api/incidents/{id}` | Session; one incident and optional automatic job |
| `GET /dashboard/api/incidents/{id}/history` | Session; saved history, limit 1–50 |

List defaults are 20 rows (history five); offsets are nonnegative and capped
at 1,000,000. Job responses reuse the sanitized existing schema and exclude
claim tokens. Missing incidents return 404. Database errors return a fixed
503 response. No original route or Bearer scope was changed.

## Troubleshooting and limits

- **Login unavailable (503):** run the setup script and restart only the API.
  Verify both environment files contain the same hash without printing it.
- **Origin/Host rejected (403):** use `127.0.0.1:8001`, not `localhost`, an IP
  alias, forwarded host, or another port. Set `DASHBOARD_ORIGIN` consistently
  and restart the API only if intentionally using another loopback address.
- **Unexpected logout:** sessions expire after one hour and are revoked on
  API restart. There is no persistent browser API credential to recover.
- **Stale indicator:** the last successful data remains visible. Check the
  database/API and use Refresh. Do not clear queues or restart n8n to fix
  a dashboard data read failure.
- **No automatic job/history:** normal for legacy incidents. The dashboard
  does not backfill or silently launch investigations.
- **Change password:** reconcile/remove only the dashboard hash entries in
  the private env files, and the generated login file if replacing it;
  rerun configuration and restart the API. Preserve both existing API tokens.

Local HTTP, one shared dashboard password, process-local sessions/rate
limits, and a trusted workstation are deliberate MVP boundaries. There are
no per-user accounts or n8n execution-history integration. Aggregates scan
existing tables; lists use bounded offset pagination, not stable cursor
snapshots under concurrent ingestion. Browser verification covers Chromium,
not Firefox/Safari, screen-reader certification, or a physical mobile device.
The current live dataset has a completed job; running/failed rendering is
covered by isolated tests rather than modifying real jobs for screenshots.
