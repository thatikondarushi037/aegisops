# Version 0.14.0 database integrity repair

## Defect and correction

Revision `ab6d946e09c9` created `uq_incidents_open_service`, a unique
PostgreSQL index on `incidents(service)` restricted to `status = 'open'`.
The SQLAlchemy model did not declare this index. Consequently Alembic's
autogenerated revision `f52e0932e446` included its removal while adding the
investigations table. The applied migration history is left unchanged.

Revision `c14a0e7d921b` restores the index, and the ORM now declares the same
name, columns, uniqueness, and predicate. It changes no records, statuses,
investigations, or foreign keys. It is forward-only; downgrade is rejected.

## Applying the repair

Run against the intended database configured by the existing DB variables:

```powershell
.\.venv\Scripts\python.exe -B -m alembic upgrade head
```

This requires an online connection and table-owner DDL privileges. The
migration obtains a PostgreSQL SHARE ROW EXCLUSIVE table lock, checks for
duplicate open services, and creates the index in the same transaction.
Readers can continue, but writes wait until the transaction ends. Schedule
accordingly for larger tables or busy environments; lock acquisition can
wait for existing transactions. Offline SQL generation is deliberately
unsupported because the duplicate preflight must execute against live data.

If duplicates exist, the migration reports their incident ID groups and
aborts without changing records or advancing the revision. Investigate those
IDs and obtain an explicit decision about the records before retrying. Do
not run the existing cleanup script automatically.

Ingestion remains HTTP 201 for a new incident and HTTP 200 for reuse of an
existing open incident, including recovery from concurrent unique-index
conflicts. No API changes are required.

## PostgreSQL tests

Run only the reviewed tests, avoiding root-level scripts with import-time
database side effects:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_migrations.py tests/test_api.py tests/test_incident.py tests/test_investigation.py -q
```

The configured server must contain a separate `aegisops_test` database. The
test role needs CONNECT and CREATE on that database. A database owner can
grant CREATE to the test role; do not grant it on the application database.
The fixture rejects use when the configured application database is itself
`aegisops_test`.

Each database test creates a uniquely named `test_v014_...` schema, restricts
its search path to that schema, runs actual Alembic upgrades, and removes
only that generated schema afterward. Existing public tables are untouched.
Tests do not create/drop databases or use metadata.create_all(). A fresh
empty schema exercises the complete migration chain without requiring
CREATEDB privileges. This does not test database provisioning itself.

Coverage includes full-chain upgrade, metadata agreement, partial uniqueness,
an existing-schema upgrade preserving all seeded history and foreign keys,
duplicate preflight rollback, and five genuinely overlapping API requests.
The concurrency test forces every initial lookup to finish before inserts
and uses independent sessions with real commits.

## Deliberate limitation

Deduplication is by exact service string, not incident fingerprint. Distinct
failures on one service reuse the same open incident, and repeated alerts do
not refresh its measurements. Different case/whitespace variants can name
different services. Historical non-open incidents remain unrestricted. This
milestone preserves those semantics; fingerprinting and normalization need
a separately reviewed lifecycle/data migration design.
